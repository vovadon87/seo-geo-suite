# Метрики и исправления

Пороги Google для полевых данных (p75): **LCP** ≤ 2,5 с хорошо, > 4 с плохо; **INP** ≤ 200 мс хорошо, > 500 мс плохо; **CLS** ≤ 0,1 хорошо, > 0,25 плохо. Вспомогательные: FCP ≤ 1,8 с, TTFB ≤ 0,8 с (ориентир). Перед выводами сверить пороги с актуальной документацией web.dev: набор метрик и значения со временем меняются.

## Откуда берутся данные и чему им верить
| Источник | Что это | Для чего |
|---|---|---|
| CrUX API / блок `loadingExperience` в PSI | поле, реальные пользователи Chrome, p75 за 28 дней | вердикт по CWV, поиск проблемных типов страниц |
| Яндекс Метрика (отчёты о скорости, если включены) | поле по вашей аудитории | сверка с CrUX, оценка по регионам и устройствам |
| GSC «Основные интернет-показатели» | поле, группы URL | какие группы страниц «плохие» |
| PSI (Lighthouse на серверах Google) | лаборатория | диагностика причин; регион замера не ваш |
| `lighthouse_run.py` | лаборатория из места запуска | повторяемая проверка до/после |
| `page_weight.py` | разбор запросов в Chromium | вес, сторонние, кэш, картинки, LCP-элемент |

Различать «поле» и «лабораторию» в каждой фразе отчёта. Расхождение нормально: лаборатория — один сценарий загрузки, поле — все реальные.

## Замер из региона аудитории
Облако и серверы Google находятся не там, где ваша аудитория. TTFB и загрузка при замере «снаружи» могут сильно отличаться от опыта пользователей в РФ и странах СНГ. Что делать:
1. Опираться на поле (CrUX по домену, Метрика), особенно для TTFB и LCP.
2. Если нужен лабораторный замер «изнутри» региона — запустить `lighthouse_run.py` и `page_weight.py` на компьютере владельца (через встроенный терминал/браузер приложения) и пометить место замера в отчёте.
3. Для проверки CDN/хостинга сравнить TTFB из двух мест (облако и компьютер владельца).
4. Не переносить выводы лабораторного TTFB на аудиторию без поля.

## Причина → исправление

### LCP (самый крупный видимый элемент)
Определить элемент: `page_weight.py` → поле `lcp_element`; в Lighthouse — «Largest Contentful Paint element». Дальше по цепочке:
1. **TTFB высокий** (>0,8 с в поле): кэш страниц на сервере, CDN, быстрее бэкенд/БД, ближе к аудитории хостинг.
2. **LCP-картинка найдена поздно:** убрать `loading="lazy"`, добавить `fetchpriority="high"`, `<link rel="preload" as="image">`, не подставлять картинку скриптом.
3. **LCP-картинка тяжёлая:** WebP/AVIF, размер под отображение (`srcset`/`sizes`), сжатие; hero не больше ~150–250 КБ как ориентир.
4. **Блокирующие CSS/JS в `<head>`:** критический CSS, остальное отложить; `defer`/`async` у скриптов.
5. **LCP — текст:** шрифты (`font-display: swap`, `preload` одного основного woff2, меньше начертаний).
6. **Клиентский рендеринг:** контент приходит скриптом → серверный рендеринг или статический HTML для первого экрана.

### INP (реакция на действия)
Лаборатория показывает косвенные признаки: TBT и long tasks (`page_weight.py`).
- Разбить долгие задачи, отложить неважные скрипты (виджеты, чаты, карты, пиксели) до первого взаимодействия.
- Сократить обработчики событий и тяжёлые перерисовки; не блокировать основной поток на клик.
- Проверка INP — только по полю (CrUX/Метрика) или в DevTools на реальных действиях.

### CLS (сдвиги макета)
- `width`/`height` или `aspect-ratio` у картинок, видео, iframe, баннеров.
- Зарезервировать место под рекламу, всплывающие плашки и cookie-баннеры (не вставлять над контентом после загрузки).
- Шрифты: `font-display` и похожий запасной шрифт; не менять размеры при подмене.
- Анимации — через `transform`/`opacity`, не через смену размеров.

### Вес и запросы
- Изображения — обычно главный вклад: WebP/AVIF, адаптивные размеры, `loading="lazy"` для картинок ниже первого экрана.
- JS: удалить неиспользуемое, разделить бандл, отложить; проверить, что подключено лишнего (старые счётчики, дубли библиотек).
- Шрифты: 1–2 семейства, woff2, только нужные начертания.
- Сторонние: перечислить в таблице (домен, вес, зачем); для каждого решение — оставить, отложить, убрать.

### Сжатие и кэш
- brotli/gzip для HTML/CSS/JS/JSON/SVG.
- Статика: `Cache-Control: public, max-age=31536000, immutable` у файлов с версией/хешем в имени; HTML — короткий кэш или `no-cache` с ETag.
- HTTP/2 или HTTP/3 включён на сервере/CDN.

### Конструкторы и CMS
- **Tilda:** встроенный оптимизатор картинок (`/-/resize/…/-/format/webp/`); первый вызов нового размера может отдать тяжёлый оригинал — «прогреть»; меньше одновременных анимаций на старте; тяжёлые блоки и виджеты — ниже первого экрана; сторонние скрипты — через вставки T123 с отложенной загрузкой.
- **WordPress:** кэш-плагин + CDN, оптимизация изображений плагином или на стороне хостинга, меньше плагинов с фронтенд-скриптами, тема без лишних библиотек.
- **Bitrix/самописные:** кэш компонентов, объединение/минификация ассетов, отключение неиспользуемых модулей на фронте.
- **Shopify/Wix/Webflow:** часть параметров не настраивается — документировать ограничение и менять то, что доступно (изображения, приложения, скрипты).

## Бюджеты (ориентиры, `scripts/budget.json`)
Общий вес до ~2 МБ, запросов до ~80, JS до ~500 КБ, CSS до ~150 КБ, изображения до ~1,2 МБ, одно изображение до ~250 КБ, сторонние до ~35% веса, TTFB до 800 мс, CLS до 0,1, long tasks суммарно до 400 мс. Это рабочие ориентиры для аудита, не требования Google. Для разных типов сайтов бюджет менять и фиксировать в профиле сайта.

## Повторный замер и учёт изменений
- Одни и те же URL, устройство, команда, число прогонов; записывать дату и условия.
- Лабораторный эффект видно сразу; полевой — с лагом до 28 дней.
- В отчёте «было → стало» отделять: что изменили, что поменялось в лаборатории, что подтверждено в поле.
