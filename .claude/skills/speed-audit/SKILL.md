# speed-audit

Измерить скорость честно, найти причины и дать исправления с проверкой. Для любого сайта, без привязки к нише и CMS. Только чтение. Общие правила — `_shared/rules.md` набора seo-geo-suite.

## Приоритеты и формат находки
P0 — мешает индексации или заявкам (дубли домена, ошибочный noindex, закрыт robots, 5xx, неверные контакты). P1 — существенно влияет на видимость/конверсию. P2 — улучшения. P3 — мелочи и эксперименты.
Находка: URL → проблема → доказательство → последствие → исправление → повторная проверка → P / уверенность / часы / зависимости / критерий готовности. В каждом отчёте: охват, что не проверено и как проверить.

## Главный принцип
Поле и лаборатория — разные вещи, и их нельзя смешивать:
- **Поле** (CrUX, Метрика): реальные пользователи, p75 за 28 дней. Только по нему можно сказать «Core Web Vitals пройдены» (LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 — все три «хорошо»).
- **Лаборатория** (PSI, Lighthouse, разбор в браузере): воспроизводимая диагностика причин. INP в лаборатории не измеряется (есть только TBT как косвенный признак).
- Лабораторные замеры сделаны **из места запуска** (облако, ваш компьютер, серверы Google). Если аудитория в другом регионе, TTFB и сетевые метрики будут отличаться. Это всегда надо оговаривать в отчёте.
- Нет записи в CrUX ≠ «плохо»: у малопосещаемых страниц данных может не быть. Тогда смотреть данные по домену (origin) и Метрику.

## Где скрипты
`scripts/` рядом с этим файлом. Что нужно:
- `psi.py`: стандартная библиотека; ключ `PSI_API_KEY` желателен (без ключа квота строгая, возможен 429).
- `crux.py`: ключ `CRUX_API_KEY` (или PSI-ключ с включённым Chrome UX Report API).
- `lighthouse_run.py`: Node.js, Lighthouse (`npm i -g lighthouse`), Chrome/Chromium; переменные `LIGHTHOUSE_BIN`, `CHROME_PATH`.
- `page_weight.py`: `pip install playwright`, Chromium.
- `speed_report.py`: стандартная библиотека.
Ключи создаёт владелец (Google Cloud Console → включить PageSpeed Insights API и Chrome UX Report API → создать ключ). Ключи не писать в отчёты, не коммитить в репозиторий. Если чего-то нет, использовать то, что есть, и записать в «Не проверено».

## Порядок работы
1. **Цель.** URL: главная + 2–4 ключевых типа страниц (категория/услуга, карточка, статья, форма). Аудитория и регион. Есть ли доступ к Метрике/GSC.
2. **Поле:** `python scripts/crux.py <url> --out audit-out` и `--origin` для домена. Без ключа — блок `loadingExperience` из `psi.py` и отчёт Метрики/GSC, о которых просим владельца.
3. **PSI:** `python scripts/psi.py <url> --strategy both --out audit-out`.
4. **Лаборатория локально:**
   `python scripts/lighthouse_run.py <url> --runs 3 --preset mobile --out audit-out` (и `desktop`). Медиана трёх прогонов; метрики с разбросом >15% помечены как нестабильные.
5. **Разбор причин:**
   `python scripts/page_weight.py <url> --device mobile --out audit-out` (с `--throttle` для приближения к мобильной сети). Показывает вес и запросы по типам, сторонние домены, сжатие, кэш, форматы и размеры картинок, блокирующие скрипты, LCP-элемент, CLS и long tasks.
6. **Отчёт:** `python scripts/speed_report.py audit-out --url <url> --region "<регион аудитории>"` → `speed-report.md`; дополнить выводами и планом по `references/metrics-and-fixes.md`.
7. **Повторный замер** после правок теми же командами в тех же условиях; в отчёт — «было → стало» с медианами и датой. Полевые метрики после правок меняются с лагом до 28 дней — так и писать.

## Как читать результат
- Начать с поля: что реально страдает (LCP, INP или CLS), на каких типах устройств.
- Затем лаборатория: **что именно** тормозит (какой LCP-элемент, сколько байт, какие скрипты).
- Приоритет по эффекту на LCP/INP/CLS, не по числу находок. Один тяжёлый hero-образ важнее десяти мелких замечаний.
- Бюджеты в `scripts/budget.json` — ориентиры; адаптировать под нишу (интернет-магазин и лендинг имеют разный допустимый вес).

## Правила
- Не писать «сайт быстрый/медленный» по одному числу Lighthouse. Диапазон, несколько прогонов, условия замера.
- Не обещать рост позиций или конверсии от ускорения. Механизм: пользователи видят контент раньше, меньше отказов на медленных сетях; влияние на ранжирование — одно из многих.
- Не рекомендовать «убрать аналитику/чат» без обсуждения: предлагать отложить загрузку.
- Нельзя править сайт без команды владельца: выдавать готовый пакет правок (что, где, значение).
- Скорость вернулась в норму ≠ задача закрыта: зафиксировать бюджеты и способ наблюдения.
